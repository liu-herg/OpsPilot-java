# P4：采购到付款业务主干（设计稿）

> 状态：已实现（第一步、第二步）。审批流与预算是 P5，权限与管理台是 P6，对账是 P7。
> 实现时和设计稿相比的调整见文末"实现时的调整"。

## 目标

现在的 OpsPilot 只有"付款执行"这一段，采购单和发票都在外部模拟系统里。P4 要把业务数据收回到系统里，从采购申请走到付款：

```
供应商
  │
采购申请 ──审批──▶ 采购订单 ──▶ 收货（可分批） ──▶ 发票登记 ──▶ 三单匹配 ──通过──▶ 付款单 ──▶ 付款执行（P1~P3 引擎）
                                                                 │
                                                              差异单 ──接受──▶ 付款单
                                                                    └─驳回──▶ 发票作废
```

## 关键决定

| 决定 | 理由 |
|---|---|
| 采购单、发票改为系统内部数据，下线 `procure-hub`、`invoice-center` 两个模拟服务 | 业务系统要拥有自己的数据；外部调用只留真正在外面的财务系统 |
| `finance-flow`（财务 / 银行付款）继续作为外部系统 | 付款是真正的外部副作用，P1~P3 的幂等、对账、崩溃恢复都围绕它，全部保留 |
| 付款单是执行引擎的唯一入口 | 每张付款单对应一次运行（`workflow_run`），引擎的状态机、租约、发件箱不用改 |
| P4 的采购申请审批先做成单级（有权限的人批准 / 驳回） | P5 用可配置的审批规则替换，P4 先把业务链路走通 |
| "一句话发起付款"保留为快捷入口 | 解析出采购单号 → 找到已匹配、未付款的发票 → 生成付款单，后面走同一条路 |
| 演示数据用初始化器写入（`opspilot.demo-data=true`），不写进 Flyway | 迁移脚本只管表结构，测试库不会混进演示数据 |

## 状态机

```
采购申请  DRAFT ─提交─▶ SUBMITTED ─批准─▶ APPROVED ─转订单─▶ ORDERED
            │               └─驳回─▶ REJECTED
            └──────────撤销─▶ CANCELLED（DRAFT / SUBMITTED 可撤销）

采购订单  ISSUED ─部分收货─▶ PARTIALLY_RECEIVED ─收齐─▶ RECEIVED ─付清─▶ CLOSED
            └─取消（没有任何收货时）─▶ CANCELLED

发票      REGISTERED ─匹配通过─▶ MATCHED ─生成付款单─▶ PAYABLE ─付款完成─▶ PAID
              └─匹配失败─▶ EXCEPTION ─接受差异─▶ PAYABLE
                                     └─驳回─▶ REJECTED

付款单    PENDING ─引擎接手─▶ EXECUTING ─▶ PAID / FAILED / REJECTED（大额审批被驳回）
```

所有状态转移沿用 P1 的写法：`UPDATE ... WHERE id = ? AND status = ?` 条件更新，状态机类检查转移是否合法。

## 三单匹配规则

发票登记时同步匹配，规则对每一行发票明细逐条检查：

| 检查 | 规则 | 不通过 |
|---|---|---|
| 供应商 | 发票供应商 = 订单供应商 | SUPPLIER_MISMATCH（直接拒绝登记） |
| 数量 | 本次开票数量 ≤ 已收货 − 已开票 | QTY_EXCEEDS_RECEIVED |
| 单价 | \|发票单价 − 订单单价\| / 订单单价 ≤ 容差（默认 1%） | PRICE_MISMATCH |
| 合计 | 明细合计 + 税额 = 价税合计（误差 ≤ 0.01） | TOTAL_MISMATCH |

- 全部通过 → MATCHED，**同一个事务里**占用开票数量（`invoiced_qty` 条件递增）并生成付款单。
- 任一不通过 → EXCEPTION，生成差异单，不占用开票数量。财务接受差异时再占用，并生成付款单；驳回则发票作废。

## 本阶段的并发问题（会写测试复现）

| 场景 | 朴素写法的问题 | 做法 |
|---|---|---|
| 同一订单行并发分批收货 | 先查已收货再加，两笔同时收货会超收 | `UPDATE po_line SET received_qty = received_qty + ? WHERE id = ? AND received_qty + ? <= quantity` |
| 两张发票同时开同一批已收货数量 | 同一批货被开两次票、付两次款 | `invoiced_qty` 同样条件递增，上限是 `received_qty` |
| 同一张发票重复登记 | 重复付款 | 唯一索引 (supplier_id, invoice_number) |
| 同一张发票重复生成付款单（重复点击、重试） | 一张发票两张付款单 | 唯一索引 invoice_id；冲突时返回已有的那张 |
| 订单状态（部分收货 / 收齐） | 并发收货时状态算错 | 收货的同一个事务里，按行汇总重新计算后条件更新 |
| 业务单号 | `MAX+1` 会重号 | `biz_sequence` 原子递增（同 P1 事件序号的思路） |

## 和执行引擎的衔接

- 付款单创建（PENDING）时，同一个事务里创建运行，并写发件箱，派发方式沿用 P3。
- 引擎的步骤从"调用外部采购 / 发票系统"改成"读内部的付款单、发票、供应商"。
  - 供应商被冻结 → FAILED（BUSINESS_VALIDATION_FAILED）。
  - 金额超过阈值 → 等待审批（P4 沿用现有的固定阈值审批，P5 换成规则）。
- 提交付款时，幂等键改为 `payment:{pay_number}`，财务系统按付款单号对账。
- 运行进入终态时，**在同一个事务里**同步付款单状态：
  - COMPLETED：付款单 → PAID，发票 → PAID；订单所有行都付清时 → CLOSED。
  - FAILED：付款单 → FAILED。可以重新发起，生成新的运行，付款单不变。
  - REJECTED：付款单 → REJECTED。

## 实现时的调整

| 设计稿 | 实际 | 原因 |
|---|---|---|
| 发票状态 REGISTERED → MATCHED → PAYABLE | 登记时直接是 PAYABLE 或 EXCEPTION | 匹配在登记的同一个事务里完成，中间状态没人看得到 |
| 付款单生成后交给引擎 | 付款单生成后是 PENDING，由财务"发起付款"（或快捷入口）才创建运行 | 真实业务里付款要人确认；演示也需要一步步来 |
| 差异都可以接受 | 数量差异不能接受，只能补收货后重新匹配 | 接受数量差异等于为没到的货付钱 |
| 引擎直接读内部单据 | 拆出 `PayableSource` 接口（付款依据 + 发票），生产实现 `LedgerPayableSource` 读内部单据；外部网关只剩财务系统 | P1~P3 的 49 个测试换成同一接口的假数据就能继续跑，不用重写 |
| 金额 long | 全链路 BigDecimal（财务模拟服务也改成两位小数） | 采购金额有分 |
| 取号 `INSERT ... ON DUPLICATE KEY UPDATE` | 独立短事务 INSERT IGNORE 建行 + 业务事务里 UPDATE 递增 | 并发插入同一个新键会死锁；行不存在时 UPDATE 会加间隙锁、挡住建行 |
| 运行终态同步付款单 | `RunStore` 在终态转移成功后同步发布 `RunFinished`，`PaymentOrderSync` 在同一个事务里更新 | 运行模块不依赖采购模块，状态又能一起提交 |

## 排查：锁住了订单，读到的却是旧数据

并发开票测试第一次跑：5 张发票同时各开 4 件（已收货 10 件），预期 2 张通过、3 张进差异单，结果有发票直接报错"可开票数量不足"。

**现象**：报错来自最后一步占用数量的条件更新 `invoiced_qty + ? <= received_qty`，也就是说三单匹配判断"数量够"，真正占用时数据库却说"不够"。

**原因**：登记发票时先用普通查询按订单号查出 id，再 `FOR UPDATE` 锁订单，然后普通查询读订单明细做匹配。MySQL 默认是可重复读隔离级别，事务里**第一次普通查询**就固定了读视图。第一步的普通查询发生在加锁之前，所以哪怕后面排队拿到了订单锁，读到的明细仍然是排队之前的旧值，每张发票都以为还剩 10 件可开。收货没有这个问题，是因为收货一开始就加锁，前面没有普通查询，但这只是碰巧。

**为什么钱没有多付**：占用数量的条件更新是当前读，它看到的是最新值，判断出数量不够，整个事务回滚。第二道防线起作用了，结果是该进差异单的发票报错了，而不是同一批货被付两次。

**修复**：按订单号直接 `FOR UPDATE`，不先做普通查询；凡是要基于"已收 / 已开票数量"做判断的地方，订单明细都用 `SELECT ... FOR UPDATE` 当前读，收货也一并改掉，不再依赖"前面没做过普通查询"这个隐含前提。

# P1：控制面（状态机 + 审批 + 付款幂等 + 事件）

## 要解决的问题

自动化执行"付款"这种有真实副作用的流程，最怕三件事：

1. **重复付款**：用户点了两次、两个实例同时跑、超时后重试……
2. **状态错乱**：两个审批人同时点了"批准"和"驳回"；运行已经失败了又被人"启动"一次
3. **不知道付没付**：请求发出去了，响应超时了

## 做了什么

**1. 状态机**（`RunStatus`）

```
QUEUED → RUNNING → READY_TO_SUBMIT → COMPLETED
            │            ▲   └→ FAILED（财务明确拒绝）
            ├→ WAITING_APPROVAL ─批准─┘
            │        └─驳回→ REJECTED
            └→ FAILED（查不到 / 数据不一致）
```

转移是否合法在 Java 里检查（非法转移是代码 bug，直接抛异常）；转移本身是一条条件更新：
`UPDATE workflow_run SET status = ? ... WHERE id = ? AND status = ?`，影响 0 行说明被别人改了。

**2. 审批**（`ApprovalService`）

一个事务里：审批单 `PENDING → APPROVED/REJECTED`（条件更新）+ 运行 `WAITING_APPROVAL → READY_TO_SUBMIT/REJECTED` + 写事件。批准后的付款在事务提交之后做。

| 情况 | 结果 |
|---|---|
| 第一个决定 | `RESOLVED` |
| 重复提交同样的决定 | `ALREADY_RESOLVED`（幂等，不报错，不会再付一次） |
| 和已有决定相反 | 409 |

**3. 付款幂等 + 对账**（`IdempotencyService`、`PaymentSubmitter`）

幂等键 = `payment:{PO}:{发票号}`，同一笔付款全局只有一条记录：

```
抢占：INSERT（成功 = ACQUIRED）
     └ 主键冲突 → UPDATE ... WHERE status='PENDING' AND lease_expires_at <= NOW()（成功 = RECLAIMED）
          └ 失败 → 看记录：COMPLETED（直接用结果）/ OCCUPIED（别人在提交，推迟）
提交前：记录是 PENDING（上次结果不明）→ 先去财务系统按业务键查，查到了直接完成
提交后：按业务键回查核实；"幂等记录完成 + 运行完成 + 事件"一个事务提交
```

提交失败按"对方有没有可能收到"分三种：

| 失败 | 例子 | 处理 |
|---|---|---|
| 肯定没发出去 | 连接被拒绝、连接超时 | 删除幂等记录，可以立即重试 |
| 不知道 | 读超时、5xx、响应丢失 | **保留** PENDING 记录，下次先对账 |
| 明确拒绝 | 4xx | 删除记录，运行 FAILED |

**4. 事件时间线**（`EventService`）

每个运行的事件序号从 1 连续递增。`GET /runs/{id}/events?after=N` 只返回新事件，P2 做实时推送时断线重连就靠它补拉。

## 设计决定（面试会问）

**1. 为什么不用分布式锁（Redisson）锁住"这笔付款"？**
锁解决的是"同一时刻只有一个人在做"，但付款要的是"**永远**只做一次"。锁释放之后，第二个人拿到锁照样会再付一次——除非他在锁里先查一下"付过没有"，而这个"付过没有"的记录就是幂等表。另外持锁的进程崩溃时，锁（靠看门狗续期）会被释放，但付款请求可能已经发出去了，下一个人拿到锁并不知道。幂等表是持久化的，PENDING 状态本身就记录了"有人发过、结果不明"。
PrismDesk 用了 Redisson 锁，是因为那里要保护的是"同一会话的内存操作别交错"，丢了重来也没关系；这里是钱，要的是持久化的事实。

**2. 租约是干什么的？为什么不直接"谁插入成功谁负责"？**
插入成功的执行者可能提交到一半崩溃了，记录永远停在 PENDING，这笔付款就再也没人处理。租约给"负责"加了期限：过期后别人可以接手。接手的判断（是 PENDING 且已过期）和修改（改成我的、attempt+1）在同一条 UPDATE 里，多个接手者只有一个影响行数为 1。
测试里对比了"先 SELECT 看是否过期，再无条件 UPDATE"：所有执行者都读到"已过期"，然后都以为自己接手成功——每个都会去发一次付款。

**3. 接手（RECLAIMED）之后能直接提交吗？**
不能直接提交，要先对账。原持有者可能已经提交成功、只是没来得及标记完成就崩溃了。所以只要记录是 PENDING，提交前都先按业务键去财务系统查一次，查到了就直接用。这也是为什么幂等键用业务键（PO + 发票号）而不是随机 UUID：对账时要能用它去对方系统查。

**4. 为什么租约时间用数据库的 `NOW()`？**
多个实例的系统时钟可能差几秒。如果 A 实例按自己的时间写了"30 秒后过期"，B 实例的时钟快了 40 秒，B 会认为租约早就过期了。判断和写入都用同一个数据库时钟就没有这个问题。

**5. 读超时为什么不能当失败处理？**
读超时说明请求已经发出去了，对方可能已经处理完，只是响应没回来。当失败重试 → 重复付款；当成功 → 可能根本没付。唯一正确的做法是"不知道就去查"。`HttpBusinessSystemGateway` 区分了连接阶段的失败（`ConnectException`、`HttpConnectTimeoutException`，肯定没发出去）和之后的失败。演示脚本里用故障注入让"财务系统处理了，但响应被丢弃"，重试时走对账，付款请求只发了 1 次。

**6. 我们有幂等，财务系统也按业务键去重，是不是重复了？**
财务系统去重是对方的实现细节，不能依赖：换一个系统可能就没有。测试里的假财务系统故意**不去重**（每次 POST 都建一笔新的），所以"只付一笔"完全是控制面自己保证的。真实环境里两层都有更好（纵深防御），演示时财务系统返回 200（已存在）会记为 `payment.duplicate_suppressed`。

**7. 审批为什么要"审批单 + 运行状态"在一个事务里？**
如果审批单改成 APPROVED 了、运行状态没改（进程在中间崩溃），这张审批单就"批了但没执行"，而且没人能再批一次（已经不是 PENDING 了）。同一事务里两边要么都改、要么都不改。如果审批单是 PENDING 而运行却不在等审批（数据不一致），直接抛异常回滚，不做半截操作。

**8. 条件更新失败后，为什么要用 `SELECT ... FOR SHARE` 再读一次？**
条件更新失败要告诉调用方"别人决定成了什么"（是 ALREADY_RESOLVED 还是 409）。MySQL 默认是可重复读：如果本事务之前做过普通 SELECT，后面的普通 SELECT 读的是事务开始时的快照，会读到"还是 PENDING"——和刚才 UPDATE 看到的（当前已提交版本）矛盾。加锁读是"当前读"，读的是最新提交的版本。

**9. 为什么付款不放在审批事务里？为什么用 `TransactionTemplate`？**
付款是 HTTP 调用，最长要等 5 秒读超时。放在事务里会让事务（和行锁、数据库连接）多挂 5 秒，并发一高连接池就被打满。而且事务回滚也撤销不了已经发出去的请求。所以原则是：**远程调用在事务外，事务里只做短的数据库操作**。
用编程式事务是因为同一个方法里既有远程调用又有好几段短事务，边界写在代码里一目了然；`@Transactional` 还要拆很多 bean 避免自调用失效。

**10. 事件序号为什么不用 `MAX(sequence) + 1`？**
两个事务同时读到同一个 MAX，然后插入时撞唯一索引（或者没有唯一索引就产生重复序号）。测试里 10 个线程同时追加，9 个失败。现在的做法是 `UPDATE workflow_run SET event_sequence = event_sequence + 1`：这条 UPDATE 拿到该运行的行锁，同一运行的追加在这里排队，读回的值一定唯一；锁到事务提交才释放，所以"分配序号"和"插入事件"是原子的。代价是同一个运行的事件追加是串行的——但一个运行本来就是顺序执行的，几乎没有争用。
（MySQL 还有个写法 `SET event_sequence = LAST_INSERT_ID(event_sequence + 1)` 再 `SELECT LAST_INSERT_ID()`，少一次读表，效果一样。）

**11. 审批单 id 为什么由运行 id 决定？**
策略步骤以后可能被重复执行（P2 故障恢复：进程在"建审批单"之后崩溃，恢复时重新执行）。审批单 id 固定为 `apr-{运行id}`，重复执行时主键冲突，沿用已有的那张，不会出现两张审批单。和 PrismDesk 里"同一会话不重复建工单"是同一个思路：**靠唯一约束兜底，而不是先查再插**。

## 已知局限

- 现在是同步执行：`POST /runs/{id}/start` 要等整个流程跑完才返回。P2 改为异步 + 启动时扫描 `QUEUED / RUNNING / READY_TO_SUBMIT` 自动恢复。
- 被推迟（OCCUPIED）或结果不明的运行要手动调 `/resume`。P2 由定时任务按 `retry_at` 自动重试。
- 审批人身份由调用方传入，没有接登录鉴权。
- 只读步骤（查采购单 / 发票）失败直接把运行标记为 FAILED，没有重试。

## 简历上这一步可以写什么

> 用 Java 重写流程自动化平台控制面：基于条件更新（CAS）的运行状态机替代 LangGraph；审批决定与运行状态转移同事务提交，并发审批仅一人生效、重复决定幂等返回；设计付款幂等记录（主键抢占 + 数据库时钟租约 + 条件回收），结合业务键对账处理"请求超时、结果未知"，在财务系统不去重的情况下，同一采购单 10 个并发运行只产生 1 次付款请求；按失败类型（未发出 / 结果未知 / 明确拒绝）区分重试策略，远程调用全部移出事务。

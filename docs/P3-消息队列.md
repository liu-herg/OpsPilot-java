# P3：事务性发件箱 + RabbitMQ 派发

## 要解决的问题

P2 里，运行被启动、审批通过、手动继续之后，由**收到请求的那个实例**直接交给自己的线程池执行（`worker.dispatch`）。这样做有四个问题：

1. **派发意图只在内存里。** 状态已经提交了，`dispatch` 还没调用进程就崩溃了，这次派发就没了，只能等恢复扫描下一轮（最多 5 秒）把运行捡起来。
2. **排队的任务会跟着进程一起卡住。** `dispatch` 先抢租约再进线程池队列。实例崩溃时，队列里排着的运行虽然一步都没执行，租约却已经在它名下，别的实例要等租约过期（60 秒）才能接手。
3. **负载不能分摊。** 哪个实例收到请求就由哪个实例执行。一个实例忙不过来，其他实例闲着也帮不上忙；它的线程池满了只能拒绝，等恢复扫描。
4. **"先提交再派发"有缝。** 如果把 `dispatch` 换成"提交后直接发 MQ"，提交成功、发 MQ 之前崩溃，消息就丢了；反过来先发 MQ 再提交，提交失败时消费者会收到一个状态根本没改的运行。

## 做了什么

```
POST /runs/{id}/start
  └─ 事务 ┬─ QUEUED → RUNNING（条件更新）
          ├─ 写事件 run.started
          └─ 写发件箱 outbox_message（PENDING）      ← 和状态变化一起提交 / 回滚
  └─ 提交后 relay.kick()
         投递器：SKIP LOCKED 领取 → 发 RabbitMQ → 等 broker 确认 → 标记 SENT
                                                   │
         RabbitMQ  opspilot.run.dispatch（持久化，prefetch=1）
                                                   │
         任意实例的消费者：抢执行租约 → 执行 → 执行完才 ack
                           抢不到（重复消息）→ 跳过并 ack
                           运行不存在 → 拒绝 → 死信队列
```

**1. 事务性发件箱**（`V3__outbox.sql`、`OutboxService`）

"要派发这个运行"写进 `outbox_message`，和触发它的状态变化**在同一个事务里**。`enqueueDispatch` 检查当前有没有事务，没有直接报错，不会悄悄自己开一个事务。

- 启动：`QUEUED → RUNNING` + `run.started` 事件 + 发件箱，一个事务。
- 审批通过：审批单 + `WAITING_APPROVAL → READY_TO_SUBMIT` + 事件 + 发件箱，一个事务。
- 手动继续：清 `retry_at` + 发件箱，一个事务。

**2. 投递器**（`OutboxRelay`、`OutboxScheduler`）

- **触发**：业务事务提交后调 `kick()` 马上投递一轮（毫秒级）。另外每秒扫一次兜底。
- **领取**：和恢复扫描同一个思路。读已提交隔离级别下 `SELECT ... FOR UPDATE SKIP LOCKED` 锁住一批到期消息，同一个事务里把 `next_attempt_at` 推后 30 秒（相当于领取租约），马上提交。网络投递在事务外。
- **确认**：RabbitMQ 开了 publisher confirm 和 mandatory。broker 把消息持久化后回 ack，消息被退回（路由不到队列）也算失败。只有收到 ack 才标记 `SENT`。
- **失败**：指数退避 2、4、8……最多 60 秒。同一轮里一条失败（多半是 MQ 连不上），剩下的直接一起推迟，不逐条等超时。失败 20 次标记 `DEAD`。
- **合并触发**：投递线程 1 个、队列长度 1，满了就丢弃这次触发。一轮会领走所有到期消息，"正在投 + 排队一轮"就够了。
- **清理**：已投递超过 7 天的消息每小时分批删除，每批 1000 条。

**3. RabbitMQ 拓扑**（`RabbitTopology`）

```
opspilot.run (direct) ──run.dispatch──▶ opspilot.run.dispatch ──拒绝──▶ opspilot.run.dlx ──▶ opspilot.run.dispatch.dlq
```

交换机、队列、消息都持久化，MQ 重启不丢。

**4. 消费者**（`RunDispatchListener`、`RunWorker.executeNow`）

- **在消费者线程里执行**，执行完才 ack（acknowledge-mode=auto）。消费者数就是执行并发数。
- **prefetch=1**：每个消费者手里最多一条，没开始执行的消息一直留在 MQ 里。实例崩溃时，它手上未确认的消息会马上重新投递给其他实例，不用等租约过期。
- **去重**：先抢执行租约（P2 的条件更新）。运行已经结束、或者正在被别人执行，就抢不到，跳过并 ack。
- **坏消息**：运行不存在、消息为空、消费时数据库出错，拒绝且不重新入队（`default-requeue-rejected=false`），进死信队列，不会无限重投。

**5. MQ 不是硬依赖**

- `dispatch.mode=local`（默认）：投递器直接交给本实例的线程池，不需要 MQ，行为和 P2 一样，只是多了发件箱。
- `dispatch.mode=mq`（docker compose 里）：投递到 RabbitMQ。
- MQ 挂了：消息留在发件箱里重试，运行由恢复扫描照样执行。RabbitMQ 的健康检查也关掉了，MQ 挂了不会让应用的 `/actuator/health` 变成 DOWN。

**6. 恢复扫描给 MQ 留宽限期**（演示时发现的问题，见下文"排查"）

MQ 派发时，恢复扫描跳过"15 秒内刚写过派发消息"的运行，它们多半正在队列里排队。过了宽限期还没人领（MQ 挂了、消费者全挂了），扫描再接手。有 `retry_at` 的运行不受影响，那是执行者自己安排的重试，不在 MQ 里。

```sql
AND (r.retry_at IS NOT NULL OR NOT EXISTS (
      SELECT 1 FROM outbox_message o
      WHERE o.message_key = r.id AND o.created_at > NOW(3) - INTERVAL 15 SECOND))
...
FOR UPDATE OF r SKIP LOCKED      -- 只锁 workflow_run，不锁发件箱
```

## 实测

### 测试（共 49 个，全部通过）

| 测试 | 结果 |
|---|---|
| 8 个投递器并发投 200 条消息，朴素写法（先查 PENDING、投递、再改 SENT） | 投出 __ 次，重复 __ 次 |
| 同样的场景，SKIP LOCKED 领取 | 投出 200 次，重复 0 次 |
| 消息已送达但确认丢了（投递器以为失败） | 重投 1 次，消费端跳过，POST 1 次 |
| MQ 不可用时启动运行 | 消息 PENDING、记下错误；恢复扫描照样跑完；MQ 恢复后补发，POST 仍是 1 次 |
| 失败达到上限 | 标记 DEAD，运行由恢复扫描完成 |
| 同一运行的派发消息又来 3 次 | 3 次都跳过，POST 1 次 |
| 业务事务回滚 | 发件箱里没有这条消息 |
| 真实 RabbitMQ：20 个运行 | 全部由 MQ 消费者执行完，每个 POST 1 次（本机 Docker 里 MySQL 单次提交就要上百毫秒，总耗时 25.9 秒，不能当性能指标） |
| 真实 RabbitMQ：派发不存在的运行 | 进死信队列 |

## 排查：恢复扫描和消费者抢活

第一次跑场景 6（两个实例，20 个运行），结果是：

| 执行者 | 个数 |
|---|---|
| app-1 消费 MQ | 7 |
| app-2 消费 MQ | 6 |
| app-1 恢复扫描 | 5 |
| app-2 恢复扫描 | 2 |

付款没有重复，但 20 个里有 7 个是恢复扫描执行的。扫描本该只是兜底，不该和消费者抢活。

**原因**：20 条消息一次性进队列，8 个消费者每人一次只拿一条，后面的消息要排几秒。排队期间运行的状态已经是 RUNNING，又还没有租约（消费者领到才会抢租约），在恢复扫描看来就是"该有人执行、却没人在执行"，于是被扫描抢走了。P2 不会出这个问题：本地派发是先抢租约再进线程池，排队的运行身上已经有租约。

**修复**：扫描时给 MQ 留 15 秒宽限期（上面第 6 点），并加了测试：停掉消费者，消息留在队列里，此时扫描不碰这个运行；把派发消息的时间改到 60 秒前，扫描就接手；消费者恢复后，那条消息被识别为重复并跳过。

**修复后**：场景 6 中 20 个运行全部由 MQ 消费，app-1 执行 12 个、app-2 执行 8 个，恢复扫描 0 个。

## 设计决定（面试会问）

**为什么要发件箱，事务提交后直接发 MQ 不行吗？**

数据库和 MQ 是两个系统，没法放进一个本地事务。"提交 → 发 MQ"之间崩溃，消息丢了；"发 MQ → 提交"，提交失败，消费者拿到一个状态根本没改的运行。发件箱把"要发什么"变成数据库里的一行，和状态变化一起提交，问题就变成"怎么把库里的行可靠地投出去"。这个可以重试，能做到至少一次。

**为什么不用分布式事务（XA）或 RocketMQ 事务消息？**

XA 要 MQ 支持，性能差，RabbitMQ 也不支持。事务消息要换 RocketMQ，还要写回查接口。发件箱只需要一张表，任何 MQ 都能用，代价是多一次数据库写入，外加一点投递延迟（`kick()` 立即触发，实际是毫秒级）。

**发件箱会重复投递吗？消费端怎么办？**

会。投递器已经投出去、还没标记 SENT 就崩溃，领取到期后会再投一次；broker 确认丢了也一样。所以是**至少一次**，不是恰好一次。消费端用 P2 的执行租约去重：抢租约是条件更新，运行已经结束或正在执行就抢不到，直接跳过。真正有副作用的付款还有 P1 的幂等记录兜底，所以哪怕租约这层漏了，也不会付两次。

**为什么领取后要提交事务再投递，不在事务里投？**

在事务里投，MQ 慢或连不上时，行锁和数据库连接会被一直占着，正好违反了这个项目"远程调用不放在事务里"的原则。代价是投递器崩溃时，消息要等 30 秒领取期过了才会被重投。

**为什么消费者要在自己的线程里执行，而不是收到消息就扔进线程池？**

扔进线程池就会马上 ack，消息离开 MQ，又回到 P2 的问题：排队的任务在内存里，进程崩溃就卡住。在消费者线程里执行、执行完才 ack，没开始执行的消息一直在 MQ 里，配合 prefetch=1，谁空闲谁拿。代价是一个消费者在执行时会一直占着一个 channel，这里并发数只有个位数，没有问题。

**消费失败为什么进死信队列，不重新入队？**

重新入队的话，坏消息（比如运行不存在）会被无限重投，把消费者打满。这里的 MQ 消息只是"尽快执行"的信号，数据库里的状态加租约才是事实来源：消息进了死信，运行还停在 RUNNING / READY_TO_SUBMIT，恢复扫描照样会接手。死信队列只用来排查。

**有了 MQ，恢复扫描还要吗？**

要，它是兜底：

- 执行中崩溃、租约过期的运行。
- 外部系统故障后按退避时间重试的运行。现在没用延迟消息，靠扫描 `retry_at`。
- MQ 挂了、发件箱放弃投递的运行。

扫描间隔保持 5 秒。正常的派发都走 MQ，扫描基本是空跑，代价是一条走索引的查询。但它要能分清"在 MQ 里排队"和"真的没人管"，所以加了宽限期（见"排查"）。

**消息的顺序有影响吗？**

没有。每条消息只是"去推进这个运行"，执行时会重新读库里的状态，按当前状态决定做什么，消息先到后到都一样。

**为什么选 RabbitMQ，不用 Kafka？**

这里要的是任务队列：每条消息只给一个消费者，ack 后删除，失败进死信，按处理能力分发（prefetch）。这正好是 RabbitMQ 擅长的。Kafka 适合高吞吐的事件流、多个消费组重复消费。用 Kafka 做任务队列的话，分区数会限制并发，单条消息失败也不好处理。

## 已知局限

- 退避重试还是靠扫描 `retry_at`，没有用延迟消息（RabbitMQ 延迟插件，或者 TTL 加死信）。
- 发件箱表是单表，投递器靠轮询加即时触发。量大以后可以改成 CDC（Canal / Debezium 读 binlog），不用轮询。
- 死信队列只是存起来，没有告警，也没有管理界面一键重放。
- 消费者在执行期间崩溃：消息会重投，但租约要等过期（60 秒）才能被别人抢到。没开始执行的消息不受影响。

## 简历上这一步可以写什么

> 引入 RabbitMQ 解耦派发与执行：用事务性发件箱让状态变化和派发消息同库同事务提交，投递器以 SKIP LOCKED 领取、publisher confirm 确认后标记，失败指数退避，至少一次投递；消费端在执行租约上去重，坏消息进死信队列，MQ 不可用时降级到恢复扫描。8 个投递器并发投 200 条消息，重复投递从 __ 次降到 0；双实例下 20 个运行由两个实例按 12 / 8 分摊执行。

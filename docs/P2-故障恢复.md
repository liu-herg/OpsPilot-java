# P2：后台执行 + 故障恢复 + 多实例

## 要解决的问题

P1 是同步执行：`POST /runs/{id}/start` 要等整个流程跑完才返回，而且有三个硬伤：

1. **进程崩溃 = 运行永远卡住。** 执行到一半进程挂了，运行停在 RUNNING，再也没人管。
2. **外部系统故障只能人工处理。** 付款超时、财务系统暂时不可用之后，运行停在 READY_TO_SUBMIT，要人去调 `/resume`。
3. **不能多实例部署。** 两个实例如果都去"捡"卡住的运行，同一个运行会被执行两次。

## 做了什么

**1. 执行租约**（`V2__run_lease.sql`、`RunWorker`）

`workflow_run` 加了 `lease_owner`（哪个实例在执行）和 `lease_expires_at`（到什么时候）。任何执行都要先抢到租约：

```
UPDATE workflow_run SET lease_owner = ?, lease_expires_at = NOW() + 60s
WHERE id = ? AND status IN ('RUNNING','READY_TO_SUBMIT')
  AND (lease_owner IS NULL OR lease_expires_at <= NOW())
```

- 执行过程中每一次状态转移都会顺便续租（相当于心跳）。
- 执行结束（不管成功失败）释放租约。
- 进程崩溃时租约留在库里，过期后就能被别人接手。

**2. 异步执行**

启动、审批通过、手动继续这三个接口都只做两件事：把状态改对（落库），再把运行交给后台线程池，然后立刻返回 202。
状态**先落库、再交出去**：交出去之后进程马上崩溃也没关系，库里的 RUNNING / READY_TO_SUBMIT 会被恢复扫描接手。

**3. 恢复扫描**（`RecoveryScheduler`）

启动时扫一次，之后每 5 秒扫一次，接手"该有人执行、但没人持有有效租约、并且到了重试时间"的运行：

```sql
SELECT id FROM workflow_run
WHERE status IN ('RUNNING','READY_TO_SUBMIT')
  AND (lease_owner IS NULL OR lease_expires_at <= NOW())
  AND (retry_at IS NULL OR retry_at <= NOW())
ORDER BY updated_at LIMIT 10
FOR UPDATE SKIP LOCKED          -- 同一事务里接着 UPDATE 标记为自己的
```

接手时在时间线上记一条 `run.picked_up`（哪个实例接手的）。

**4. 外部故障自动重试（指数退避）**

| 情况 | 处理 |
|---|---|
| 查采购单 / 发票时业务系统不可用 | 留在 RUNNING，5s、10s、20s… 后重试，**5 次后才失败** |
| 付款连接失败（肯定没发出去） | 释放幂等记录，退避后重新提交 |
| 付款结果不明（超时、响应丢失） | 保留幂等记录，退避后**先对账**；结果不明的付款不自动放弃（退避最长 5 分钟） |
| 别人正在提交同一笔 | 等对方的幂等租约到期 |

`retry_at` 和 `retry_count` 都在数据库里，进程重启也不会丢。

**5. 防"僵尸执行者"（fencing）**

后台执行时，每一次状态转移的 WHERE 里都带 `lease_owner = 我`。如果执行者卡住了（长时间 GC、网络分区），租约过期被别的实例接手，它醒过来后就改不动状态了。

**6. 演示用的崩溃注入**

`POST /chaos/crash-after-submit`：下一次付款请求成功后，立刻 `Runtime.halt()`。这和 `kill -9` 一样，`finally` 和 shutdown hook 都不会执行。容器配置了自动重启，重启后：

1. 启动时发现本实例名下还挂着租约，判断上次进程是异常退出的，直接释放，不用干等 60 秒过期。
2. 恢复扫描接手这个运行。
3. 幂等记录还是 PENDING，于是先去财务系统按业务键对账，发现已经付过了，直接完成，不会再付一次。

## 实测

> 测试：37 个全部通过；演示：`scripts/demo.ps1` 全部 5 个场景符合预期（2026-11-11，Docker 里的 MySQL 8.4）。

| 测试 | 场景 | 结果 |
|---|---|---|
| `MultiInstanceClaimTest` | 4 个实例同时扫描 40 个待恢复运行，"先 SELECT 再 UPDATE" | **40 个全部**被多个实例同时领走（每个都会被执行多次） |
| | 同样条件，`FOR UPDATE SKIP LOCKED` | 40 个全部领完，重复 0 个。两次运行各实例分到 31/8/1/0 和 40/0/0/0：领取本身只要几毫秒，先启动的线程常常一口气领完，分配不均不影响正确性 |
| `RecoveryTest` | 执行者崩溃（RUNNING，租约过期） | 被接手并完成，付款 1 次 |
| | 租约还有效（别的实例正在执行） | 不接手 |
| | 付款已发出后崩溃 | 对账完成，POST 1 次，付款 1 笔 |
| | 采购系统连续 2 次不可用 | 退避重试 2 次后完成 |
| | 采购系统一直不可用 | 5 次重试后 FAILED（UPSTREAM_UNAVAILABLE），不付款 |
| | 租约被接手后，旧执行者尝试转移状态 | 被拒绝 |
| 演示场景 4 | 付款成功后 `halt` 进程 | 崩溃时财务系统已有 PAY-C23A81DA；容器自动重启后 `run.picked_up` → `payment.reconciled` → COMPLETED，付款单仍是 PAY-C23A81DA，**没有第二笔** |

### 演示里的两段时间线

付款响应丢失（场景 3），不需要人工操作：

```
11. submission.started
12. submission.ambiguous   （5 秒后自动重试）
13. run.picked_up          （恢复扫描接手）
14. payment.reconciled     （按业务键查到已付款，不再提交）
15. side_effect.verified
16. run.completed
```

付款成功后进程被强杀（场景 4）：

```
10. submission.started
    ── 进程 halt，容器自动重启，启动时释放本实例遗留的租约 ──
11. run.picked_up
12. payment.reconciled
13. side_effect.verified
14. run.completed
```

最终财务系统：PO-10001、PO-10002、PO-10004 各 1 笔，PO-10003（校验失败）没有。

## 设计决定（面试会问）

**1. 为什么用数据库租约，不用 Redis 分布式锁？**
要保护的是"运行"这行数据，执行权和状态在同一张表里：抢租约、转移状态、续租都是对同一行的条件更新，天然一致。如果锁放在 Redis，就会出现"锁在 Redis、状态在 MySQL"两边对不上的情况。比如拿到了锁，可是状态已经被别人改了；或者锁过期了，状态还在改。另外，不多引入一个组件，也就少一个故障点。代价是每次续租都要写一次库，不过续租本来就附带在状态转移里，没有额外的写。

**2. `SKIP LOCKED` 解决什么问题？不用会怎样？**
多个实例同时扫描时：
- **普通 SELECT 再 UPDATE**：大家查到同一批候选，然后都标记成自己的，同一个运行被执行多次。测试里 4 个实例扫 40 个运行，40 个全部被重复领走。
- **`FOR UPDATE` 不加 `SKIP LOCKED`**：不会重复了，但第二个实例会卡在第一个实例锁住的那批行上，等它提交以后才能继续，相当于串行。
- **`FOR UPDATE SKIP LOCKED`**：被别人锁住的行直接跳过，各领各的，互不等待。这就是"用数据库表当任务队列"的标准做法。

**3. 扫描事务为什么用读已提交（READ COMMITTED）？**
MySQL 默认是可重复读。在这个级别下，`FOR UPDATE` 会对扫描过的索引范围加**间隙锁**，扫描期间新插入的运行（新建任务）会被挡住；不满足条件的行也会一直锁到事务结束。读已提交下没有间隙锁，不满足 WHERE 的行会立即解锁。所以扫描事务用单独的 `TransactionTemplate`，并且设成读已提交。

**4. 恢复时从哪一步继续？为什么敢"从头重放"？**
RUNNING 状态的运行被接手后会**从第一步重新执行**，不去记"做到第几步"。这样做是安全的，原因有三个：
- 前面的步骤只是查询和确定性的校验，重放没有副作用；
- 审批单 id 由运行 id 决定，重放时主键冲突，会沿用已有的那张；
- 唯一有副作用的付款不在 RUNNING 阶段，而是在 READY_TO_SUBMIT 阶段，由幂等记录加对账保证只做一次。

"每一步都可重放，有副作用的那一步做幂等"，这比精确记录断点简单得多，也不容易出错。

**5. 什么是 fencing？为什么有了租约还需要它？**
租约只能保证"同一时刻最多一个人**认为**自己有执行权"，挡不住一个**已经失去**执行权、自己却还不知道的执行者。比如 A 在 GC 停顿了 70 秒，租约过期，B 接手；A 醒过来后会继续往下执行。所以每次写状态时都要验证"我还是持有者"（`AND lease_owner = 'A'`），这就是 fencing。它和 ZooKeeper / etcd 里用 fencing token 防脑裂是同一个思路。
测试里做了这样一个场景：B 接手之后，A 再去转移状态，被拒绝了。

**6. 进程重启后，为什么能立即接手，而不用等 60 秒租约过期？**
实例 ID 默认取主机名。容器重启后主机名（容器 ID）不变，所以新进程启动时如果发现库里还有自己名下的租约，就能确定那是上一次进程留下的（同一个 ID 不可能同时有两个进程在跑），直接释放就行。前提是实例 ID 必须唯一，多实例部署时每个实例的主机名不能重复，也可以用 `INSTANCE_ID` 环境变量显式指定。

**7. 线程池满了怎么办？为什么不用 CallerRunsPolicy？**
队列满了直接拒绝，同时马上释放刚抢到的租约，下一轮恢复扫描会再领。不用 CallerRunsPolicy，是因为调用方可能是处理 HTTP 请求的线程，让它去跑一整个流程（多次远程调用），接口就会被拖慢。运行已经落库了，晚几秒执行不要紧。PrismDesk 用 CallerRunsPolicy，是因为那里的任务必须在本次请求里完成，丢了就没有了。

**8. 停机时正在执行的运行怎么办？**
开了优雅停机：`server.shutdown=graceful`，线程池设置 `waitForTasksToCompleteOnShutdown` 并最多等 30 秒，正常停机时会等它们跑完。超过 30 秒或者是被强杀的，租约会留在库里，重启后（或者其他实例在租约过期后）接手。**所以不管怎么停，都不需要人工处理。**

**9. 退避重试的次数和时间存在哪里？**
`retry_at` 和 `retry_count` 都在 `workflow_run` 表里，而且由数据库时钟计算（`DATE_ADD(NOW(3), INTERVAL ? SECOND)`）。如果放在内存里（比如 `ScheduledExecutorService.schedule`），进程一重启就丢了，而且多个实例之间也看不到彼此的安排。

## 已知局限

- 恢复扫描是轮询（默认 5 秒），一个运行最慢要等一轮才会被重试或接手。P3 引入消息队列后，可以改成"状态变化发消息"，扫描只做兜底。
- 只读步骤每次恢复都从头重放，如果某一步很昂贵（比如调大模型），应该加步骤级的结果缓存。
- 时间线现在只能轮询 `GET /runs/{id}/events?after=N`，下一步做 WebSocket 实时推送（多实例之间用 Redis Pub/Sub 广播）。
- 结果不明的付款会一直重试对账，需要配合告警（比如 `retry_count` 超过阈值），交给人工处理。

## 简历上这一步可以写什么

> 实现流程运行的后台执行与故障恢复：基于数据库行级租约（条件更新抢占、状态转移即续租）保证同一运行同时只有一个执行者，状态写入附带租约持有者校验（fencing）防止失联执行者误写；恢复扫描使用 `SELECT ... FOR UPDATE SKIP LOCKED` 支持多实例并行领取（4 实例 40 个待恢复运行零重复，普通"先查后改"写法下 40 个全部被重复领取）；外部系统故障按指数退避持久化重试；演示中付款成功后强制 kill 进程，重启后自动对账完成，未重复付款。
